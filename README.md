# AML Transaction Monitoring — ML Risk Ranker

A Python + scikit-learn project for Anti-Money Laundering (AML) detection using tabular transaction and KYC data. The system is a **risk ranker**: it scores every customer by fraud probability and outputs a prioritised list for investigator review, rather than making binary fraud/not-fraud decisions.

## Overview

The pipeline ingests raw KYC and transaction data for 1,000 bank customers, engineers behavioural and demographic features, trains a logistic regression classifier, and produces a ranked list of customers ordered by their AML risk score.

**Key design decision — ranker, not classifier:**
Binary classification metrics (accuracy, F1) are misleading at 1% fraud prevalence. The model is evaluated as a ranker: *"if an investigator reviews the top N customers by score, what fraction of known fraud cases do they find?"*

Current performance (logistic regression baseline, test set):
| Review top N | Fraud found | Recall |
|---|---|---|
| Top 10 | 7 / 10 | 70% |
| Top 20 | 7 / 10 | 70% |
| Top 50 | 8 / 10 | 80% |

## Feature Engineering

Features fall into two categories: KYC-derived and transaction-derived.

### KYC Features (`src/features/kyc_features.py`)

| Feature | Type | Description |
|---|---|---|
| `customer_type` | Categorical | `individual` or `smallbusiness` |
| `is_individual` | Binary | 1 for individuals, 0 for businesses |
| `age_years` | Numeric | Age in years (individuals only; NaN for businesses) |
| `account_tenure_days` | Numeric | Days since onboarding (NaN if onboard date missing) |
| `income` | Numeric | Reported annual income |
| `occupation_code` / `occupation_title` | Categorical | Enriched from reference table |
| `income_occupation_flag` | Binary | 1 if income > $50k AND occupation is UNEMPLOYED or STUDENT |
| `employee_count` / `sales` | Numeric | Business headcount and revenue |
| `business_age_days` | Numeric | Days since business was established |
| `days_established_to_onboard` | Numeric | Gap between founding and account opening — a shell company signal (NaN if onboard date missing) |
| `revenue_per_employee` | Numeric | Sales divided by employee count; both zero and implausibly high values are suspicious |
| `industry_code` / `industry` | Categorical | Enriched from reference table |

### Transaction Features (`src/features/tx_aggregates.py`)

For each of the 7 channels, the following aggregates are computed per customer:

| Feature | Description |
|---|---|
| `{ch}_count` | Total transaction count |
| `{ch}_amt_sum` | Total transaction volume (CAD) |
| `{ch}_amt_mean` | Average transaction size |
| `{ch}_amt_max` | Largest single transaction |
| `{ch}_active_days` | Distinct days with activity |
| `{ch}_credit_sum` | Total inflows |
| `{ch}_debit_sum` | Total outflows |
| `{ch}_net_flow` | Inflows minus outflows |
| `{ch}_avg_per_day` | Transaction count normalised by active days |

**Channel-specific extras:**

| Feature | Channel | Description |
|---|---|---|
| `abm_cash_count` | ABM | Cash withdrawal count |
| `abm_cash_rate` | ABM | Cash withdrawals as fraction of all ABM transactions |
| `abm_unique_province` | ABM | Number of distinct provinces used |
| `abm_unique_city` | ABM | Number of distinct cities used |
| `card_ecom_count` / `card_ecom_rate` | Card | E-commerce transaction count and rate |
| `card_foreign_count` / `card_foreign_rate` | Card | Foreign transaction count and rate |
| `card_unique_mcc` | Card | Number of distinct merchant category codes |
| `card_unique_province` / `card_unique_city` | Card | Geographic spread of card usage |

**Total: 94 input features** (84 numeric, 10 categorical) → 454 features after one-hot encoding.

Large transaction CSVs are read in chunks of 750,000 rows to avoid memory issues.

## Pipeline

The full pipeline is orchestrated by `src/train.py` and runs four stages in order:

```
build → split → train → eval
```

```
Raw CSVs
   │
   ▼
[build]  src/data/build_table.py
         Joins labels + KYC + 7 transaction aggregates
         → Data/Processed/joined/train_table.parquet  (1000 rows × 97 cols)
   │
   ▼
[split]  src/data/make_splits.py
         Stratified 70/15/15 split preserving fraud rate
         → Data/Processed/splits/{train,valid,test}.parquet
   │
   ▼
[train]  src/model/train_baseline.py  (or train_xgb.py)
         Fits sklearn Pipeline: impute → scale → logistic regression
         → models/logreg_baseline.joblib
         → models/logreg_baseline.meta.json
   │
   ▼
[eval]   src/model/evaluate.py
         Computes Recall@K, ROC-AUC, PR-AUC on valid and test splits
         → reports/metrics/logreg_baseline.{valid,test}.json
```

## Models

### Logistic Regression Baseline (`logreg_baseline`)

The current production model. sklearn `Pipeline`:
1. **Numeric columns** — `SimpleImputer(median)` → `StandardScaler`
2. **Categorical columns** — `SimpleImputer(most_frequent)` → `OneHotEncoder(handle_unknown="ignore")`
3. **Classifier** — `LogisticRegression(class_weight="balanced", solver="saga", max_iter=5000)`

Datetime columns are dropped. `class_weight="balanced"` compensates for the 99:1 class imbalance.

### XGBoost + SMOTE (`xgb_smote`, experimental)

An alternative model that applies SMOTE oversampling before fitting an XGBoost classifier. Underperforms the logistic regression on this dataset due to the very small number of fraud training cases (7), which limits SMOTE's ability to generate diverse synthetic examples. Kept as a reference for when more data becomes available.

## Evaluation

Because the model is a **risk ranker**, the primary metrics are:

| Metric | Description |
|---|---|
| **Recall@K** | Fraction of known fraud cases found in the top K ranked customers |
| **ROC-AUC** | Overall ranking quality (1.0 = perfect separation, 0.5 = random) |
| **PR-AUC** | Precision-recall tradeoff across all thresholds |
| **Rank of positives** | Exact rank of each known fraud case in the sorted list |

Threshold-based metrics (accuracy, F1, confusion matrix) are included in the evaluation output for completeness but are not used to assess model quality.

## Quick Start

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

### 2. Run the full pipeline

```bash
python -m src.train
```

This runs all four stages (build → split → train → eval) and saves the model and metrics.

### 3. Generate the risk ranking

```bash
python -m src.score
```

Outputs a ranked CSV and console summary showing which customers are highest risk.

## Running Individual Steps

### Train only (data already built)

```bash
python -m src.train --skip-build
```

### Run specific stages

```bash
python -m src.train --stages train eval
```

### Train the XGBoost model

```bash
python -m src.train --model xgb --skip-build
```

### Score with a specific model

```bash
python -m src.score --model-name xgb_smote --top 50
```

### Run diagnostics (feature signal audit)

```bash
python -m src.diagnostics
```

Checks three things: label counts end-to-end, join quality (do fraud rows have transaction data?), and univariate signal per feature. Useful for debugging model underperformance.

### Risk Flags

The ranked customer CSV includes a `risk_flags` column with human-readable notes for investigators:

| Flag | Trigger condition |
|---|---|
| `high income for occupation` | UNEMPLOYED or STUDENT with income > $50,000 |
| `student` / `unemployed` | Occupation code match |
| `account < 1 year old` | Account tenure under 365 days |
| `onboarded <30 days after business founding` | Shell company indicator |
| `business < 6 months old` | Established date within 180 days |
| `employees but zero revenue` | Has headcount but $0 sales |
| `implausibly high revenue/employee` | Revenue per employee above 95th percentile |
| `has wire transfers` | Any wire transfer activity |
| `high EMT volume (top 10%)` | EMT total above 90th percentile |
| `high EFT outflows (top 10%)` | EFT debit total above 90th percentile |
| `30%+ foreign card transactions` | High foreign card usage rate |
| `high cheque activity (top 10%)` | Cheque count above 90th percentile |

## Known Limitations & Next Steps

### Current limitations

- **Small dataset** — only 10 confirmed fraud cases. Evaluation metrics (especially PR-AUC) are highly sensitive to the ranking of a single case and should be interpreted cautiously.
- **No temporal features** — transactions are aggregated across all time. A customer with 10 wire transfers in one week looks identical to one who spread them over 2 years. Velocity and recency features would significantly improve detection.
- **Two fraud cases are poorly ranked** — one atypical geographic profile (rank 226) and one high-revenue business (rank 999) are not well captured by the current features.

### Suggested next steps

1. **Velocity features** — rolling 30/90/180-day windows for transaction counts and volumes; burst detection
2. **Network/graph features** — shared counterparties across wire/EMT transactions; structuring ring detection
3. **Explainability** — SHAP values per prediction for compliance justification
4. **EDA notebooks** — exploratory analysis of label distributions and feature correlations in `NoteBooks/`
